# Profiling Report — FlowerShopApi

**Модуль:** 3 — Якість, продуктивність і надійність програмного забезпечення  
**Проєкт:** FlowerShopApi (ASP.NET Core / .NET 10, Entity Framework Core, MySQL)  
**Гілка:** `quality/module-3`  
**Дата дослідження:** 06.11.2026  
**Досліджуваний endpoint:** `GET /api/products`

## 1. Мета

Оцінити поведінку застосунку під навантаженням, проаналізувати використання потоків і пам'яті, знайти потенційні джерела накладних витрат та експериментально перевірити можливість оптимізації доступу до даних без небажаних змін API.

## 2. Середовище та інструменти

- **Сервер:** локально запущений `FlowerShopApi` через `dotnet run`, HTTP `http://localhost:5239`.
- **База даних:** MySQL 8.0 у Docker, доступ із Windows через `localhost:3307` (порт контейнера 3306).
- **Моніторинг:** `dotnet-counters`.
- **Трасування:** `dotnet-trace`, файл `flowershop-profile.nettrace`.
- **Навантаження:** k6 у Docker через `http://host.docker.internal:5239/api/products`, 10 VU протягом 30 секунд, без `sleep()`.
- **Допоміжні перевірки:** ApacheBench (ab), HTTP-відповіді через PowerShell.

**Важливо:** для локального API під час дослідження використовувався правильний порт MySQL `3307`. Раніше порт `3306` повертав інший результат (`[]`), тому порівнювані вимірювання проводилися після виправлення конфігурації підключення.

## 4. Аналіз трасування dotnet-trace

Зібрано трасування працюючого процесу під навантаженням k6:

```powershell
dotnet-trace collect --process-id <PID> --output flowershop-profile.nettrace

dotnet-trace report flowershop-profile.nettrace topN --number 30

dotnet-trace report flowershop-profile.nettrace topN --number 30 --inclusive
```

### 4.2. Висновок за трасуванням

Вибірки переважно припали на внутрішні методи очікування та обслуговування потоків .NET. **Ці частки не є відсотками активного CPU-споживання** та не доводять проблем із ThreadPool. У доступному звіті `topN` не було встановлено конкретного CPU-вузького місця у власному коді FlowerShopApi.

## 5. Аналіз коду і гіпотеза оптимізації

У `FlowerShopApi/Repositories/ProductRepository.cs` метод `GetAllAsync()` початково використовував EF Core із відстеженням змін:

```csharp
return await _context.Products
    .Include(p => p.Category)
    .ToListAsync();
```

**Гіпотеза:** вимкнення відстеження сутностей при читанні може зменшити накладні витрати EF Core. Для перевірки порівняно три реалізації:

1. Стандартний tracking-запит (початковий код).
2. `AsNoTracking()`.
3. `AsNoTrackingWithIdentityResolution()`.

При цьому `Product` і `Category` мають навігаційні властивості в обидва боки. Відстеження та identity resolution можуть впливати на об'єктний граф і, отже, на JSON при серіалізації безпосередньо EF-сутностей.

## 6. Вимірювання до та після (k6)

**Умови:** `GET /api/products`, локальний API, k6 через Docker, 10 VU, 30 с, без пауз між запитами. Вимірювання — одиничні запуски кожного варіанта; вони не є статистично значущим бенчмарком.

| Метрика | Початковий tracking | `AsNoTracking()` | `AsNoTrackingWithIdentityResolution()` |
|---|---:|---:|---:|
| Кількість запитів | 68 432 | 85 077 | 63 775 |
| Throughput, запитів/с | 2 280,71 | 2 835,86 | 2 125,71 |
| Середня затримка | 4,29 мс | 3,43 мс | 4,61 мс |
| p95 | 6,37 мс | 4,80 мс | 7,10 мс |
| Максимальна затримка | 18,39 мс | 819,88 мс | 85 мс |
| HTTP-помилки | 0% | 0% | 0% |
| JSON-відповідь | 11 183 Б | 4 910 Б | 11 183 Б |
| Кількість товарів після запиту | не перевірено окремо до експериментів | 12 | 12 |

Під час використання `AsNoTracking()` швидкість у конкретному запуску зросла приблизно на **24,3%**, але одночасно зменшився розмір відповіді на **56,1%**. Тому цей результат не можна вважати чистим прискоренням без зміни контракту відповіді.

У випадку `AsNoTrackingWithIdentityResolution()` розмір JSON повернувся до 11 183 Б, але пропускна здатність в одиничному запуску виявилася приблизно **на 6,8% нижчою** за початковий варіант. Однаковий розмір не гарантує побайтової або семантичної тотожності JSON.

## 7. Підсумкове рішення щодо коду

- `GetAllAsync()` **повернуто до початкового tracking-запиту**: без підтвердженого прискорення за незмінної відповіді зміну залишати недоцільно.
- `GetByIdAsync()` **не змінювався**: сутність використовується для `UpdateAsync()`/`DeleteAsync()`, де необхідне коректне відстеження для `SaveChangesAsync()`.
- Для `GetOutOfStockAsync()` розглянуто/залишено `AsNoTracking()` як локальну оптимізацію читання. **Окремого вимірювання її ефекту ще не було**, тож прискорення не заявляється.
- Для `GetByCategoryIdAsync()` рекомендовано зберігати вихідну поведінку з `Include(p => p.Category)` та відстеженням до перевірки незмінності JSON-контракту.

**Статус перевірки:** користувач повідомив, що `dotnet test FlowerShopApi.sln` після внесених змін завершився успішно. Для остаточного коміту потрібно повторити тести після фінального стану `GetByCategoryIdAsync()` (якщо його змінено після останнього запуску тестів).

## 8. Додаткові спостереження: ApacheBench

Під час тестування локального API з контейнера ApacheBench через `host.docker.internal` деякі триваліші запуски завершувалися тайм-аутами, наприклад:

- `-n 3000 -c 20 -s 60`: завершено 2749 запитів до переривання.
- `-n 1000 -c 10 -s 15`: завершено 611 запитів до переривання.

Натомість k6 із 10 VU без пауз виконав **68 432 запити за 30 с без помилок**. Тому причина тайм-аутів ApacheBench не встановлена: можливі особливості клієнта, з'єднань або шляху Docker ↔ Windows. Їх **не можна приписувати підтвердженому дефекту MySQL чи API** без додаткових вимірювань.

## 9. Висновок

Профілювання виконано засобами `dotnet-counters` та `dotnet-trace`; показники порівняно з результатами навантажувального тестування k6. Виявлено **потенційні накладні витрати EF Core на відстеження та формування графа сутностей**, що є кандидатом на оптимізацію. Водночас випробувані зміни у `GetAllAsync()` не забезпечили доведеного виграшу **за незмінного контракту API**, тому цей метод повернуто до вихідної реалізації. Конкретне CPU-вузьке місце за трасуванням не підтверджене.
