# Завдання 10 — Caching (кешування)

**Проєкт:** FlowerShopApi  
**Технології:** ASP.NET Core (.NET 10), Entity Framework Core, MySQL, `IMemoryCache`  
**Мета:** зменшити кількість повторних звернень до бази даних під час отримання каталогу товарів та забезпечити оновлення кешу після CRUD-операцій.

## 1. Постановка завдання

Реалізувати кешування результату отримання списку товарів. Повторні запити протягом визначеного часу повинні повертати дані з оперативної пам’яті без нового SQL-запиту. Після створення, редагування або видалення товару кеш необхідно інвалідувати, щоб наступний запит отримав актуальні дані з БД.

## 2. Обраний підхід

Використано вбудований механізм **In-Memory Caching** (`IMemoryCache`). Кешування винесено на рівень `ProductService`, а не в демонстраційний `ProductsV2Controller`. Це забезпечує спільне використання кешу маршрутами:

- `GET /api/products` — основний (legacy) маршрут;
- `GET /api/v1/products` — версія API v1;
- `GET /api/v2/products` — версія API v2, що перетворює результат сервісу на DTO.

У `Program.cs` зареєстровано сервіс `builder.Services.AddMemoryCache()` **до** `builder.Build()`. Залежність `IMemoryCache` передається до `ProductService` через конструктор (Dependency Injection).

## 3. Реалізація кешування

У `ProductService.GetAllAsync()` використовується ключ **`products:all`** та час життя кешу **30 секунд (TTL)**.

Принцип роботи:

1. Сервіс перевіряє наявність запису `products:all` за допомогою `TryGetValue()`.
2. Якщо запис знайдено (**CACHE HIT**), повертається список товарів з оперативної пам’яті.
3. Якщо запису немає (**CACHE MISS**), сервіс викликає `IProductRepository.GetAllAsync()`, отримує список із MySQL та зберігає його через `Set()` із TTL 30 секунд.
4. Після завершення TTL наступний запит знову отримує дані з БД і формує новий запис кешу.

Приклад основного фрагмента:

```csharp
private const string ProductsCacheKey = "products:all";

public async Task<List<Product>> GetAllAsync()
{
    if (_cache.TryGetValue(ProductsCacheKey, out List<Product>? cachedProducts)
        && cachedProducts != null)
    {
        _logger.LogInformation("CACHE HIT: товари отримано з кешу");
        return cachedProducts;
    }

    _logger.LogInformation("CACHE MISS: отримання товарів із БД");
    var products = await _productRepository.GetAllAsync();
    _cache.Set(ProductsCacheKey, products, TimeSpan.FromSeconds(30));
    return products;
}
```

Логування `CACHE HIT` / `CACHE MISS` дозволяє наочно визначати джерело даних під час демонстрації.

## 4. Інвалідація після CRUD

Після **успішного** збереження змін у базі даних викликається:

```csharp
_cache.Remove(ProductsCacheKey);
```

Цей виклик розміщено після `await _productRepository.SaveChangesAsync()` у трьох методах `ProductService`:

| Операція | Метод | Дія з кешем |
|---|---|---|
| Створення товару | `CreateAsync()` | Видалення `products:all` після `SaveChangesAsync()` |
| Оновлення товару | `UpdateAsync()` | Видалення `products:all` після `SaveChangesAsync()` |
| Видалення товару | `DeleteAsync()` | Видалення `products:all` після `SaveChangesAsync()` |

Таким чином після CRUD наступне читання списку має виконати новий SQL-запит. Якщо зміни не вдалося зберегти, інвалідація після `SaveChangesAsync()` не виконується.

**Примітка:** інвалідація після CRUD описує внесену реалізацію. Окремий ручний сценарій `PUT → GET` або автоматизований тест інвалідації в наданих результатах не підтверджений.

## 5. Ручна перевірка

Запуск API:

```powershell
dotnet run --project FlowerShopApi/FlowerShopApi.csproj
```

Три послідовні запити:

```powershell
1..3 | ForEach-Object {
    Invoke-WebRequest `
        -Uri "http://localhost:5239/api/products" `
        -UseBasicParsing | Out-Null
    Start-Sleep -Seconds 1
}
```

**Фактично зафіксовані логи:**

```text
CACHE MISS: отримання товарів із БД
Executed DbCommand ... SELECT ... FROM products ...
CACHE HIT: товари отримано з кешу
CACHE HIT: товари отримано з кешу
```

Результат: **три успішні виклики отримання каталогу, один SQL-запит на завантаження списку та два повторні використання кешу**. У цьому конкретному сценарії вдалося уникнути **2 з 3 (приблизно 66,7%)** звернень до БД за списком товарів. Це результат невеликої демонстрації, а не загальна оцінка продуктивності системи.

## 6. Сумісність із тестами

Після додавання `IMemoryCache` змінився конструктор `ProductService`: тепер він приймає `IProductRepository`, `ILogger<ProductService>` і `IMemoryCache`. Попередні тестові файли, де сервіс створювався вручну, отримали **13 помилок компіляції CS7036** через відсутній аргумент `cache`.

Виклики конструктора оновлено у:

- `UnitTests/ProductServiceTests.cs` — 5 місць;
- `MockingTests/ProductMockingTests.cs` — 4 місця;
- `ExceptionTests/ProductExceptionTests.cs` — 4 місця.

У тестових сценаріях передається окремий `MemoryCache(new MemoryCacheOptions())`; логіку перевірок (`Assert`) змінювати не потрібно. **До впровадження кешування було підтверджено 58 успішних тестів. Повторний результат усього набору після виправлення конструктора в наданих матеріалах не наведено**, тому остаточну кількість успішних тестів після зміни слід зафіксувати командою:

```powershell
dotnet test FlowerShopApi.sln
```

## 7. Обмеження та можливі покращення

- `IMemoryCache` працює лише в пам’яті одного процесу. Після перезапуску API кеш очищається; кілька екземплярів сервісу матимуть окремі кеші.
- Кешується `List<Product>` (EF Core-сутності). Для складнішої системи доцільно кешувати незалежні DTO або незмінні копії даних.
- Послідовність `TryGetValue()` / `Set()` не запобігає кільком одночасним зверненням до БД під час паралельного `CACHE MISS`.
- Наразі кешується лише `GetAllAsync()`. Отримання за ID, категорією та списку відсутніх товарів не кешується окремо.
- Інші шляхи зміни товарів поза `ProductService` можуть вимагати додаткової інвалідації.
- Для production із кількома серверами можна розглянути розподілений кеш (наприклад, Redis), метрики hit/miss та відповідну стратегію інвалідації.

## 8. Висновок

У FlowerShopApi реалізовано кешування каталогу товарів на рівні `ProductService` засобами `IMemoryCache` з TTL 30 секунд. Кеш спільний для legacy, v1 та v2 маршрутів. Після операцій створення, оновлення й видалення передбачено очищення кешу після успішного збереження даних.

Ручна перевірка **підтвердила роботу `CACHE MISS` і `CACHE HIT`**: із трьох послідовних запитів лише перший призвів до SQL-запиту. Повторне проходження повного набору тестів після зміни конструктора залишається окремою перевіркою.
