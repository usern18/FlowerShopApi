# FlowerShopApi
## Структура гілок проєкту (Branching Strategy)

У нашому командному проєкті використовується чітка стратегія організації гілок, яка забезпечує зручну паралельну розробку та перевірку коду перед інтеграцією:

* **`main`** (або **`master`**)
  * **Призначення:** Стабільна, фінальна версія проєкту, повністю готова до розгортання або здачі. Код сюди не пишеться напряму - усі зміни потрапляють лише на фінальному етапі через злиття готової роботи.

* **`develop`**
  * **Призначення:** Головна робоча гілка поточної розробки. Це спільна база, куди інтегруються всі виконані завдання після проходження перевірки (Code Review) від учасників команди.

* **`feature/products-controller`**
  * **Призначення:** Робоча гілка для розробки функціоналу роботи з товарами (каталог, ендпоїнти контролера продуктів, пагінація та управління товарами в магазині).

* **`docs/swagger-api`**
  * **Призначення:** Гілка для технічної документації, зокрема для налаштування та генерації документації API за допомогою Swagger/OpenAPI.

* **`feature/user-auth`**
  * **Призначення:** Робоча гілка для реалізації системи аутентифікації та авторизації користувачів (реєстрація, логін, робота з JWT-токенами).

* **`feature/app-dbcontext`**
  * **Призначення:** Робоча гілка для налаштування контексту бази даних (`AppDbContext`), підключення Entity Framework Core та створення моделей сутностей.

* **`design/database-schema`**
  * **Призначення:** Гілка для проектування структури бази даних, налаштування зв'язків між таблицями (1:1, 1:N, N:M) та перевірки відповідності нормам нормалізації (3НФ).

* **`docs/readme`**
  * **Призначення:** Гілка для створення та оформлення основного файлу `README.md` в корені репозиторію (опис проєкту, інструкції із запуску, технологічний стек та склад команди).
