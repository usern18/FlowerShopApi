# Звіт із завдання 8 — API Versioning

**Проєкт:** FlowerShopApi (ASP.NET Core, .NET 10)  
**Модуль:** 3 — якість, надійність і підтримка API  
**Тема:** Версіонування REST API зі збереженням зворотної сумісності  
**Дата:** 06.11.2026

## 1. Мета

Реалізувати декілька версій API для ресурсу товарів, зберегти працездатність попередніх клієнтів, продемонструвати відмінності між контрактами v1 і v2 та перевірити сумісність автоматизованими тестами.

## 2. Початковий стан

У проєкті вже існував `ProductsController` із базовим маршрутом `api/[controller]` та операціями отримання товарів, отримання товару за ID, фільтрації за категорією, перегляду товарів без залишку, створення, оновлення й видалення. Контролер використовував `ProductService`, а адміністративні операції захищалися атрибутом `[Authorize(Roles = "admin")]`.

До змін API працював, зокрема, за маршрутом `GET /api/products`. Необхідно було розширити маршрути без зміни контракту цього ендпоінта.

## 3. Реалізація

### 3.1. Збереження попереднього маршруту та додавання v1

До наявного `ProductsController` додано другий атрибут маршруту:

```csharp
[ApiController]
[Route("api/[controller]")]
[Route("api/v1/[controller]")]
public class ProductsController : ControllerBase
```

Це дозволяє використовувати як `/api/products`, так і `/api/v1/products` без дублювання коду. Обидва маршрути використовують наявні дії контролера, сервіс і формат відповіді. Додатковий маршрут поширюється на відповідні GET, POST, PUT та DELETE-методи цього контролера; обмеження доступу для адміністративних операцій залишаються чинними.

### 3.2. Контракт API v2

Створено DTO `FlowerShopApi/DTOs/Products/ProductV2Dto.cs` із такими властивостями:

| Поле | Тип | Призначення |
|---|---|---|
| `Id` | `int` | Ідентифікатор товару |
| `Name` | `string` | Назва товару |
| `Price` | `decimal` | Ціна |
| `InStock` | `bool` | Чи доступний товар і чи є позитивний залишок |
| `AvailableQuantity` | `int` | Кількість товару на складі |

Створено `FlowerShopApi/Controllers/ProductsV2Controller.cs` із базовим маршрутом `api/v2/products`. Реалізовані ендпоінти:

- `GET /api/v2/products` — список товарів у форматі v2;
- `GET /api/v2/products/{id}` — один товар у форматі v2.

`ProductsV2Controller` повторно використовує `ProductService`; перетворення моделей `Product` на `ProductV2Dto` відбувається в окремому методі `ToV2Dto`. Значення `InStock` визначається умовою `StockQuantity > 0 && IsAvailable`.

### 3.3. Порівняння контрактів

**Приклад v1 (скорочене представлення об'єкта `Product`):**

```json
{
  "productId": 5,
  "name": "Букет півоній",
  "price": 650,
  "stockQuantity": 7,
  "isAvailable": true
}
```

**Приклад v2 (DTO):**

```json
{
  "id": 5,
  "name": "Букет півоній",
  "price": 650,
  "inStock": true,
  "availableQuantity": 7
}
```

Приклади ілюструють структуру контрактів, а не повний знімок поточної бази даних. У v1 повертається наявна модель товару, а у v2 — вибрані поля DTO зі зміненими назвами і додатковим обчислюваним полем `inStock`.

## 4. Забезпечення зворотної сумісності

Маршрут `/api/products` залишено чинним, тож наявні клієнти можуть продовжувати використовувати старі адреси. Також додано явний маршрут `/api/v1/products` з аналогічною поведінкою. Впровадження v2 не змінює бізнес-логіку `ProductService` та не вимагає зміни репозиторію чи структури БД.

Водночас новий контракт v2 не є повністю взаємозамінним зі старим: клієнт, що очікує `productId` або `stockQuantity`, має використовувати v1 чи адаптуватися до `id` та `availableQuantity`.

## 5. Автоматизоване тестування

У проєкті `FlowerShopApi.ProductTests` додано `VersioningTests/ProductVersioningTests.cs`. Тести використовують `ProductTestFactory`, HTTP-запити до тестового застосунку та Moq для підміни `IProductRepository`.

| Сценарій | Очікуваний результат |
|---|---|
| `GET /api/products` | HTTP 200, попередні назви полів |
| `GET /api/v1/products` | HTTP 200, попередні назви полів |
| `GET /api/v2/products` | HTTP 200, контракт DTO v2 |
| `GET /api/v2/products/5` | HTTP 200, дані товару у форматі v2 |
| `GET /api/v1/products/99999` | HTTP 404 |
| `GET /api/v2/products/99999` | HTTP 404 |

**Команди запуску:**

```powershell
dotnet test FlowerShopApi.ProductTests/FlowerShopApi.ProductTests.csproj --filter "FullyQualifiedName~ProductVersioningTests"
dotnet test FlowerShopApi.sln
```

**Фактичний результат, підтверджений виконавцем:** усі **58 із 58** тестових випадків solution пройшли успішно. До реалізації версіонування проходили 52 тестові випадки; додано шість випадків, які перевіряють URL-маршрути та контракти.

Додатково вручну перевірено, що `/api/products`, `/api/v1/products` та `/api/v2/products` доступні, а вміст відповіді v2 відрізняється від попереднього формату.

## 6. Обмеження та можливе вдосконалення

Поточна реалізація використовує **URL path versioning через атрибути маршрутизації ASP.NET Core**, без бібліотеки `Asp.Versioning.Mvc`. Це підходить для демонстрації сумісності маршрутів і відмінностей контрактів, однак не надає автоматичного визначення версій, звітності про підтримувані/застарілі версії та розділених OpenAPI/Swagger-документів.

У поточній v2 реалізовані лише два GET-ендпоінти. Операції створення, оновлення, видалення та додаткові запити залишаються доступними у старому маршруті та v1. Для повного промислового API слід визначити політику підтримки версій, окрему документацію та правила виведення застарілих контрактів з експлуатації.

Також доцільно перевіряти незмінність контрактів v1 та v2 у CI/CD при майбутніх змінах DTO й моделей.

## 7. Висновок

У FlowerShopApi реалізовано URL-версіонування ресурсу товарів зі збереженням старого маршруту та формату відповіді у v1. Для v2 створено окремий контролер і DTO, що дозволяє еволюціонувати контракт API без дублювання сервісної логіки. Зворотну сумісність, новий формат та обробку відсутнього товару перевірено автоматизованими тестами; повний набір із 58 тестів пройдено успішно.
