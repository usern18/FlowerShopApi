# Звіт із перевірки безпеки API (API Security)

**Проєкт:** FlowerShopApi — REST API інтернет-магазину квітів  
**Модуль:** 3 — якість, надійність і безпека програмного забезпечення  
**Завдання:** 7 — API Security  
**Дата:** 06.11.2026

## 1. Мета роботи

Проаналізувати захист REST API, перевірити механізми автентифікації та авторизації, валідацію вхідних даних і розмежування доступу до ресурсів. Усунути виявлені недоліки, перевірити залежності на відомі вразливості та підтвердити працездатність автоматизованими тестами.

## 2. Початковий стан системи

У FlowerShopApi вже були реалізовані JWT-автентифікація, рольова авторизація ASP.NET Core та DTO з атрибутами валідації. У `Program.cs` налаштовано перевірки JWT: `ValidateIssuer`, `ValidateAudience`, `ValidateLifetime` та `ValidateIssuerSigningKey`. Для адміністративних методів контролерів використовуються атрибути на зразок `[Authorize(Roles = "admin")]`, а для користувацьких — `[Authorize]`.

Було проведено перевірку `OrdersController`, `UsersController`, `OrderService`, `CurrentUserService` та DTO замовлень.

## 3. Виявлені проблеми та виконані зміни

### 3.1. Недостатня перевірка власника замовлення (IDOR)

**Проблема.** Ендпоінт `GET /api/orders/{id}` вимагав автентифікацію через `[Authorize]`, проте викликав `OrderService.GetByIdAsync(id)`, який перевіряв лише існування замовлення. Звичайний авторизований користувач потенційно міг отримати замовлення іншого користувача, знаючи його ідентифікатор. Це приклад порушення контролю доступу на рівні об'єкта (IDOR / Broken Object Level Authorization).

**Виправлення.** Для користувацького маршруту застосовано метод `GetMyOrderByIdAsync(id)`: він отримує ідентифікатор поточного користувача з JWT, знаходить замовлення та перевіряє `order.UserId == userId`. Для неіснуючого або чужого замовлення повертається `404 Not Found`, щоб не розкривати факт існування чужого ресурсу. Адміністративний доступ до списку замовлень залишається окремо через `GET /api/orders` з вимогою ролі `admin`.

### 3.2. Валідація кількості товарів

У `CreateOrderItemDto` **вже існувала** перевірка:

```csharp
[Range(1, int.MaxValue)]
public int Quantity { get; set; }
```

Контролер позначений `[ApiController]`, тому некоректне значення `Quantity` відхиляється на етапі валідації моделі з відповіддю `400 Bad Request`. Дублювання цієї перевірки в `OrderService` не є необхідним для звичайного HTTP-сценарію. Це наявний механізм безпеки, а не новостворена валідація.

### 3.3. Обробка ідентифікатора поточного користувача

У `CurrentUserService` покращено отримання `ClaimTypes.NameIdentifier`: замість прямого `int.Parse` використовується `int.TryParse` з перевіркою коректності ідентифікатора. За відсутності або некоректності ідентифікатора генерується відповідний виняток авторизації.

### 3.4. Зберігання конфіденційних налаштувань

JWT-ключ і рядок підключення до MySQL прибрано з `appsettings.json` і перенесено до **.NET User Secrets** для локального середовища `Development`.

- Локальний API на Windows підключається до MySQL-контейнера через опублікований порт `3307`.
- Усередині Docker Compose доступ до MySQL має налаштовуватися через ім'я сервісу та внутрішній порт `3306`.
- Для контейнерного/продукційного запуску необхідно передавати секрети через змінні середовища або спеціалізоване сховище секретів. User Secrets не є механізмом конфігурації production-контейнерів.
- Значення, які раніше були розкриті або потрапили в історію Git, необхідно замінити перед розгортанням. Переміщення до User Secrets саме по собі не скасовує попереднього розкриття.

Після перенесення конфігурації локальний API було успішно запущено.

### 3.5. Діагностика помилок сервера

У `ExceptionHandlingMiddleware` додано логування непередбачених винятків через `ILogger<ExceptionHandlingMiddleware>` із фіксацією HTTP-методу та шляху запиту. Клієнт, як і раніше, отримує узагальнену відповідь `500 Internal Server Error` без внутрішнього стеку викликів.

### 3.6. Ізольована конфігурація тестового середовища

Після винесення JWT-ключа з `appsettings.json` шість тестів проєкту `FlowerShopApi.ProductTests` почали повертати `500`. Логи підтвердили причину:

```text
IDX10703: Cannot create a 'SymmetricSecurityKey', key length is zero.
```

Тестовий сервер працює в середовищі `Testing`, де User Secrets автоматично не завантажувалися. Додано `ProductTestFactory` із **окремим, несекретним тестовим JWT-ключем** та налаштуваннями issuer/audience. Фабрика зберігає реальну перевірку JWT і наявні підміни репозиторіїв через Moq. Очікувані коди відповідей тестів (`200`, `401`, `404`) не змінювалися для приховування помилки.

### 3.7. Перевірка залежностей NuGet

Було усунуто раніше зафіксовані попередження щодо пакета `Microsoft.Extensions.Http.Resilience` (`NU1603`) та вразливого транзитивного `MySqlConnector` (`NU1902`). Після оновлення залежностей команда перевірки повідомила, що у проєкті FlowerShopApi **не виявлено пакетів із відомими вразливостями за налаштованими джерелами NuGet**.

Перевірка залежностей не гарантує повної відсутності вразливостей у застосунку.

## 4. Тестування безпеки

Додано або перевірено автоматизовані сценарії для таких ситуацій:

| Сценарій | Очікувана поведінка |
|---|---|
| Запит захищеного маршруту без JWT | `401 Unauthorized` |
| Запит адміністративного маршруту звичайним користувачем | `403 Forbidden` |
| Передавання `Quantity = -5` під час створення замовлення | `400 Bad Request` |
| Запит захищеного маршруту з некоректним JWT | `401 Unauthorized` |
| Запит чужого замовлення за ID | `404 Not Found` |
| Отримання власного замовлення | `200 OK` |
| Адміністратор змінює статус замовлення | Успішна зміна за дозволеним маршрутом |

Після виправлення IDOR було адаптовано E2E-сценарій: адміністратор перевіряє статус через дозволений маршрут `GET /api/orders`, а не через маршрут для власних замовлень іншого користувача.

**Фінальний результат виконання `dotnet test FlowerShopApi.sln`: 52 із 52 тестів пройшли успішно** (за підтвердженням результату запуску). Раніше зафіксовані шість помилок через порожній тестовий JWT-ключ усунено.

Команди перевірки:

```powershell
dotnet test FlowerShopApi.sln
dotnet list FlowerShopApi/FlowerShopApi.csproj package --vulnerable --include-transitive
```

## 5. Залишкові ризики та рекомендації

1. **Deployment:** налаштувати `Jwt__Key` та `ConnectionStrings__DefaultConnection` для Docker/production без зберігання справжніх секретів у репозиторії; протестувати запуск контейнерів окремо.
2. **Ротація секретів:** замінити раніше розкриті JWT-ключ і пароль MySQL; за необхідності переглянути історію Git та відкликати скомпрометовані значення.
3. **Додаткові тести JWT:** окремо перевірити прострочений токен, неправильний підпис і невідповідність `issuer`/`audience`.
4. **Контроль доступу:** доповнити тест ізоляції замовлень сценарієм із двома звичайними користувачами (без адміністративної ролі).
5. **Конфігурація:** додати явну перевірку критично важливих налаштувань під час запуску, щоб відсутній ключ не спричиняв `500` на першому HTTP-запиті.
6. **Діагностика:** зберігати структуровані логи серверних винятків без розкриття секретів і внутрішніх деталей API-клієнтам.

## 6. Висновок

У межах завдання **API Security** проаналізовано JWT-автентифікацію, рольову авторизацію, валідацію DTO та контроль доступу до замовлень. Виявлено й усунуто проблему доступу до чужого замовлення за ID, удосконалено обробку ідентифікатора користувача та логування винятків. Конфіденційні налаштування для локальної розробки перенесено до User Secrets, а тестове середовище отримало ізольовану конфігурацію JWT.

**Результат:** усі **52 автоматизовані тести** пройдено успішно; перевірка NuGet не виявила відомих вразливих пакетів у поточній конфігурації джерел. Перед публічним розгортанням необхідні ротація раніше розкритих секретів і окрема перевірка production/Docker-конфігурації.
